# Connexion avec Google / GitHub : ce qui protège le parcours

Configuration des fournisseurs : voir le [README](../README.md#connexion-avec-google--github-facultatif). Code : `backend/oauth.py` et `backend/routers/auth.py`, tests : `backend/tests/test_oauth.py`.

- **Flux « authorization code » côté serveur**, avec **PKCE** (S256) et un **`state`** aléatoire. Les deux sont gardés dans un cookie HttpOnly, SameSite=Lax, signé et valable 10 minutes (Secure dès que l'API est en https), et le `state` est comparé à temps constant au retour. Un retour qui ne vient pas du départ de ce navigateur est refusé, et le code n'est jamais échangé.
- **Identité vérifiée** : l'id_token de Google est contrôlé (signature RS256 avec les clés publiques de Google, émetteur, audience = notre client, expiration ; 60 s de tolérance d'horloge). Pour GitHub, l'identité vient de son API, et seule l'adresse **principale et vérifiée** est retenue.
- **Rattachement de comptes** : une identité déjà liée retrouve son compte (même si l'adresse a changé chez le fournisseur). Sinon, un compte existant avec la même adresse est rattaché, **uniquement si le fournisseur l'a vérifiée** (sans cela, n'importe qui pourrait s'emparer d'un compte en déclarant son adresse). Sinon, un compte sans mot de passe est créé. Un compte peut être lié à Google et à GitHub à la fois.
- **Une adresse confirmée par Google / GitHub l'emporte : l'ancien mot de passe est supprimé et les sessions existantes fermées.** L'inscription par mot de passe ne vérifie pas l'adresse : quelqu'un pourrait créer un compte avec l'adresse de sa victime avant elle, puis attendre qu'elle s'y connecte via Google pour lire ses tableaux. Au premier rattachement d'un compte à mot de passe, le mot de passe est donc effacé et toutes ses sessions sont révoquées (`users.token_version`, recopié dans chaque jeton et vérifié à chaque requête comme à l'ouverture du WebSocket ; les WebSocket déjà ouverts sont fermés sur toutes les instances). Le propriétaire légitime ne perd rien d'autre que son mot de passe : il se connecte désormais via le fournisseur. Ajouter ensuite un second fournisseur ne ferme rien, le compte ayant déjà été confirmé.
- **Pas de jeton dans une URL** : au retour, l'application reçoit un **code de connexion à usage unique** (60 s, seul son condensé est en base, donc valable quelle que soit l'instance qui le reçoit), qu'elle échange par `POST /api/auth/exchange` contre la session.
- **Code lié à l'onglet de départ (contre le « login CSRF »)** : un attaquant pourrait mener sa propre connexion, garder le lien de retour et l'envoyer à sa victime, qui se retrouverait connectée à **son** compte sans le savoir. Le bouton tire donc un nonce aléatoire (256 bits) gardé en `sessionStorage` par l'onglet ; il voyage dans le cookie d'état signé et l'échange exige le même : un lien reçu d'ailleurs est inutilisable, et le code est consommé dès la première tentative (pas de second essai). En plus, si l'onglet est déjà connecté à un autre compte, l'application demande avant de changer de compte.
- **Pas d'énumération** : un compte créé via Google ou GitHub n'a pas de mot de passe ; s'y connecter par mot de passe renvoie le même 401 qu'un mot de passe faux.
- Toute erreur (refus de l'utilisateur, `state` invalide, jeton refusé, adresse non vérifiée, fournisseur injoignable) renvoie vers l'écran de connexion avec un message clair, jamais vers une erreur brute.
